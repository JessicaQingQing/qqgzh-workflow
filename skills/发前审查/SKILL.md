# 发前审查

审查是一道**阻断闸门**。不通过就不能走发布步骤。你来执行这些检查——直接读 HTML，逐条对，逐条报 PASS 或 FAIL。

## 检查哪些

读 `references/audit-checklist.yaml` 拿当前完整的检查清单。总项数是动态的——运行时从这个文件算出来，不写死。

## 检查类别

| 类别 | 查什么 |
|------|--------|
| 结构 | HTML 有没有 `<article>` 或 `<body>`？有没有 `<h1>` 大标题？ |
| CSS 安全 | 有没有微信会吞掉的写法？`position: fixed/sticky`、`@import`、`<script>`、`<iframe>`、`<form>`、`<input>`、`<button>`——这些都不能有 |
| 图片 | 如果用了 `<img>`，每个 `src` 是不是以批准的主机名开头（默认只认 `https://mmbiz.qpic.cn/`）。一个图都没有 → 直接 PASS |
| 要点 | 文章是否包含读者能带走的核心观点或金句（`.takeaway` 区块） |
| 商业连接 | 如果商业连接方案声明了要加 `.connect` 或 `.cta`，检查是否存在且格式正确。如果没有声明，这些项不检查 |
| 隐私与敏感信息 | 没有本地路径（`C:\...`、`/Users/...`、`/home/...`），没有 API Key 样子的字符串，没有凭据标记 |
| 事实可追溯 | （内容层检查）文章里的事实性陈述是否有可辨识的来源或标注——是用户亲身经历、用户确认过的公开信息、还是需要读者自行验证 |
| 第三方脱敏 | （内容层检查）文中的真实人物、公司、客户是否已去除可识别信息（除非有明确授权） |

## 怎么审

1. 打开生成的 HTML 文件
2. 读 `references/audit-checklist.yaml` 获取当前完整的检查清单
3. 逐条对照检查，需要的话逐行看
4. 每条报 PASS 或 FAIL，加一句简短说明
5. 统计通过数：`审查通过：N/N` 或 `审查未通过：M/N`

## 审查结果处理

- **审查通过：N/N** ——可以往下走了。问用户确认发布。
- **审查未通过：M/N** ——告诉用户哪些没过、怎么改、必须重新审查通过才能走发布步骤。

审查通过是发布的必要条件，不是充分条件——用户还要亲自确认才能发。

## 商业连接的审查逻辑

不是每篇文章都需要商业连接。审查时根据商业连接的决策来判断：

- **商业连接声明"不需要"**：跳过 `.connect`、`.cta` 和软广相关检查。标记为 `SKIP`（不纳入总数）。
- **商业连接声明"需要连接入口"**：检查是否有 `.connect` 区块。
- **商业连接声明"需要商业落点"**：检查 `.cta` 区块是否存在、占比是否合理、是否有紧迫感或虚假承诺。

## 与旧版本的差异

- 审查不再强制要求 `.connect` 区块
- 新增内容层的检查（事实可追溯、第三方脱敏）
- 检查项总数由 `audit-checklist.yaml` 动态计算，不写死数字
